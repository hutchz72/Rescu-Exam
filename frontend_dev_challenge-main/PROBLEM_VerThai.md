# Rescu — Flutter Developer Assessment (คู่มือและข้อกำหนดภาษาไทย)

ยินดีต้อนรับสู่ **Rescu** แอปพลิเคชันตลาดอาหารส่วนเกินขนาดเล็ก (mini surplus-food marketplace) ที่เปิดให้ผู้ใช้เรียกดูดีลลดราคาช่วงท้ายวันจากร้านค้าใกล้เคียง เพิ่มลงในถุง และนัดหมายรับสินค้าตามช่วงเวลาของร้าน แอปนี้จำลองโครงสร้างและเทคโนโลยีที่ใช้งานจริง ได้แก่ **GetX** (State management, Dependency Injection, Routing), โครงสร้างแบบ Layer-first, โมเดล JSON ที่เขียนด้วยมือ, `flutter_map` และรายการแบบแบ่งหน้า (Paginated lists)

แอปทำงานแบบออฟไลน์โดยสมบูรณ์ผ่านบริการจำลอง backend ใน `lib/service/fake_api_service.dart` ซึ่งมีการจำลองความหน่วง (latency) และข้อผิดพลาดเป็นระยะ โดยไม่จำเป็นต้องใช้ API key หรือบัญชีผู้ใช้ใดๆ

## กฎพื้นฐาน (Ground rules)

1. **อนุญาตและคาดหวังให้ใช้เครื่องมือ AI** สามารถใช้ Cursor, Copilot, Claude, ChatGPT หรือเครื่องมืออื่นๆ ตามความถนัดได้ โดยคุณต้องรับผิดชอบโค้ดทุกบรรทัดที่ส่ง และสามารถอธิบายที่มาและการทำงานได้ในการสอบสัมภาษณ์
2. **ห้ามแก้ไข** ไฟล์ `lib/service/fake_api_service.dart` หรือไฟล์ใดๆ ใน `assets/data/` ซึ่งเปรียบเสมือนส่วนของ Backend
3. **ห้ามอัปเกรด** Flutter หรือแพ็กเกจใดๆ ในโปรเจกต์ เครื่องมือถูกล็อกเวอร์ชันไว้ที่:
   - **Flutter 3.27.0**
   - **Java 17** (สำหรับการบิลด์ Android)
   - *ข้อยกเว้น:* หากใช้เครื่อง iPhone จริงที่มี iOS 26 ในการทดสอบ สามารถใช้ Flutter **3.38.10** ได้
4. **คอมมิทงานอย่างสม่ำเสมอ** แยก 1 การเปลี่ยนแปลงที่สมบูรณ์ต่อ 1 คอมมิท พร้อมข้อความที่สื่อความหมายชัดเจน (เช่น `[RES-101] Fix search race condition...`)
5. บันทึกระยะเวลาที่ใช้ในการทำแบบทดสอบตามจริงไว้ใน `solutions.md`

## ส่วนที่ A — ตั๋วแก้บั๊ก (Part A — Bug tickets)

สำหรับตั๋วทุกใบที่คุณเลือกทำ: **จำลองปัญหา (Reproduce), หาสาเหตุที่แท้จริง (Root cause), แก้ไขอย่างถูกวิธี และเขียนสรุปการวินิจฉัยลงใน `solutions.md`**

> *หมายเหตุ:* การแก้ปัญหาแบบซ่อนอาการ (เช่น การกดข้าม Error, การใส่ try/catch ดักไว้เฉยๆ หรือการบังคับ Rebuild) จะได้คะแนนน้อยกว่าการระบุสาเหตุที่ถูกต้องแม้ไม่ได้เขียนโค้ดแก้

### RES-101 · ค้นหาแสดงผลลัพธ์ผิดคำค้น (Search shows results for the wrong query)
- **อาการ:** พิมพ์คำค้นหาอย่างรวดเร็วทีละตัวอักษร (เช่น "sushi") มักพบว่าผลลัพธ์สุดท้ายไม่ตรงกับคำที่อยู่ในช่องค้นหา โดยผลลัพธ์ที่ถูกต้องจะปรากฏขึ้นแป๊บเดียว แล้วถูกทับด้วยผลลัพธ์ของคำค้นก่อนหน้าที่สั้นกว่า

### RES-102 · แอปพังหลังจากออกจากหน้า My orders (Crash after leaving My orders)
- **อาการ:** เปิดหน้า **My orders** ในขณะที่มีคำสั่งซื้อที่รอการรับสินค้า จากนั้นกด Back ออกมา ภายใน 2-3 วินาที แอปจะพังในโหมด Debug พร้อมข้อความ `setState() called after dispose()`

### RES-103 · คำขอสะสมมากขึ้นเรื่อยๆ ตามเวลาการใช้งาน (Requests pile up the longer you browse)
- **อาการ:** หลังจากเปิดดูหน้าดีลหลายๆ หน้า ทุกครั้งที่กด "Add to bag" จะเกิดการส่งคำขอ `GET /deals/:id` รัวๆ โดยส่งไปยังทุกดีลที่เคยเปิดดูในเซสชันนั้น แม้ว่าหน้านั้นจะถูกปิดไปนานแล้วก็ตาม แอปจะช้าลงและมีการรับส่งข้อมูลมากขึ้นเรื่อยๆ

### RES-104 · ดีลซ้ำในหน้าฟีดหลัก (Duplicate deals in the home feed)
- **อาการ:** เลื่อนลงไปล่างสุดของฟีดหลักเพื่อให้โหลดหน้าถัดไป แล้วรีบดึงลงเพื่อรีเฟรช (Pull-to-refresh) ทันทีในขณะที่กำลังโหลด ผลลัพธ์คือฟีดเกิดรายการดีลซ้ำ หรือมีจำนวนรายการเกินกว่าแคตตาล็อกจริง

### RES-105 · ฟีดหลักกระตุกและหน่วยความจำเพิ่มขึ้นเรื่อยๆ (Home feed is janky and memory keeps climbing)
- **อาการ:** บนอุปกรณ์ Android ระดับกลาง หน้าฟีดหลักมีอาการเฟรมตกอย่างเห็นได้ชัดขณะเลื่อน และการใช้หน่วยความจำเพิ่มขึ้นเรื่อยๆ จนระบบปฏิบัติการสั่งปิดแอป DevTools แสดงให้เห็นว่าฟีดทั้งหน้าถูก Rebuild ตลอดเวลาขณะเลื่อน และ Image cache ขยายตัวอย่างรวดเร็ว

### RES-106 · เวลาการรับสินค้าผิดพลาด และตัวกรอง "Pickup today" ขาดข้อมูลบางรายการ (Wrong pickup times; "Pickup today" filter misses deals)
- **อาการ:** ร้านเบเกอรี่ที่เปิดเวลา **06:00–09:30** กลับแสดงผลเป็น "Pick up 23:00 – 02:30" บนการ์ด และร้านค้าที่มีรอบรับสินค้าวันนี้บางร้านไม่ปรากฏเมื่อเปิดตัวกรอง **Pickup today** โดยฝั่ง Backend ยืนยันว่าส่งข้อมูล ISO-8601 UTC มาตรฐานถูกต้องแล้ว

### RES-107 · Deep link เปิดแล้วแอปพัง (Deep link opens to a crash)
- **อาการ:** เมื่อเปิดลิงก์แจ้งเตือน เช่น `rescu://open/deal?id=42&source=push` แอปจะพังด้วยข้อความ `type 'Null' is not a subtype of type 'DealModel'` แต่ถ้าเปิดดีลเดียวกันจากหน้าแรกกลับใช้งานได้ปกติ
- **ข้อกำหนด:** ลิงก์ต้องพาผู้ใช้ไปยังหน้าดีลที่ใช้งานได้สมบูรณ์ (ดีล id 42 มีอยู่ในระบบ) การแสดงหน้า Fallback/Error ไม่ถือเป็นการแก้ไขที่ยอมรับได้

## ส่วนที่ B — ฟีเจอร์ใหม่ (Part B — Features)

### F-1 · นับถอยหลัง Flash Sale แบบเรียลไทม์ (Live flash-sale countdowns)
เปลี่ยนป้าย "Ends soon" ของ Flash deal (`flashSaleEndsAt`) ให้เป็น **ตัวนับถอยหลังแบบสด** (`mm:ss` หรือ `hh:mm:ss` หากเกิน 1 ชั่วโมง) ในทุกจุดที่แสดงดีล (Flash rail, การ์ดหน้าแรก, หน้ารายละเอียด)
- **ข้อกำหนด:**
  - เมื่อตัวนับถอยหลังถึง 0: การ์ดต้องเปลี่ยนเป็นสถานะ "Expired" (กดเพิ่มใส่ถุงไม่ได้) และหากอยู่ในถุงสินค้าแล้ว ต้องถูกนำออกพร้อมแสดงข้อความแจ้งเตือน
  - หน้าฟีดหลักต้องเลื่อนได้อย่างลื่นไหล แม้มีตัวนับถอยหลังมากกว่า 100 รายการ การ Rebuild ทุกๆ วินาทีต้องจำกัดขอบเขตเฉพาะข้อความเวลาที่เปลี่ยนเท่านั้น (ห้าม Rebuild ทั้งการ์ดหรือทั้งลิสต์)

### F-2 · ติดตามการมองเห็นรายการดีล (Impression tracking)
บันทึกสถิติการมองเห็นการ์ดดีลผ่าน `AnalyticsService`:
- ส่งอีเวนต์ `deal_impression` เมื่อการ์ดดีลแสดงผลบนหน้าจอ **$\ge$50% เป็นเวลาต่อเนื่องอย่างน้อย 1 วินาที** (ข้อมูลที่บันทึก: `deal_id`, `source`, `position`)
- บันทึก **สูงสุด 1 ครั้ง ต่อดีล ต่อแอปเซสชัน**
- จัดกลุ่มการส่ง (Batch): ส่งผ่าน `FakeApiService.sendAnalyticsBatch` เมื่อสะสมครบ 10 อีเวนต์ **หรือ** ผ่านไป 15 วินาทีนับจากอีเวนต์แรกที่ยังไม่ได้ส่ง
- ต้องไม่กระทบต่อประสิทธิภาพการเลื่อนหน้าจอ (Scrolling performance)

### F-3 · จองสต็อกสินค้าล่วงหน้าพร้อม UI แบบ Optimistic (Stock reservations with optimistic UI)
สร้างระบบจองสต็อกในถุงสินค้า (ระบบ Backend มี API `reserveDeal`, `releaseReservation` และการส่ง `reservationId` ในการชำระเงิน โดยการจองมีอายุ **5 นาที**):
- การเพิ่มสินค้าลงถุงจะทำการจองสต็อก โดย UI ต้องตอบสนองแบบ **Optimistic** (แสดงผลทันที) แล้วทำการ Reconcile หากการจองล้มเหลว ให้ย้อนคืนรายการออกจากถุงพร้อมแจ้งเตือนด้วยภาษาที่เข้าใจง่าย
- แต่ละรายการในถุงต้องแสดงเวลาที่เหลือของการจอง
- การลบรายการหรือลดจำนวน ต้องทำการยกเลิก/ปรับเปลี่ยนการจองสต็อก
- การชำระเงินต้องส่ง `reservationId` และรองรับการจัดการเมื่อเกิด Error `410 reservation expired`
- **การตัดสินใจเชิงผลิตภัณฑ์:** กำหนดและออกแบบพฤติกรรมของแอปเองเมื่อการจองหมดอายุในขณะที่ผู้ใช้กำลังใช้งาน หรืออยู่ระหว่างการชำระเงิน พร้อมเขียนอธิบายเหตุผลลงใน `solutions.md`

## ส่วนที่ C — เอกสารส่งมอบ (Part C — Written deliverables)

สร้างไฟล์ **`solutions.md`** ไว้ที่ Root ของโปรเจกต์ โดยครอบคลุมหัวข้อต่อไปนี้:

1. **รายละเอียดของแต่ละตั๋ว/ฟีเจอร์ที่ทำ:**
   - Root cause (สำหรับบั๊ก) — สาเหตุที่แท้จริง
   - เหตุผลที่เลือกวิธีแก้ปัญหานี้ พร้อมระบุแนวทางอื่นที่พิจารณาแต่ปฏิเสธไป
   - Edge cases ที่คำนึงถึง และอันที่ตัดสินใจไม่จัดการพร้อมเหตุผล
2. **บันทึกการใช้ AI (AI usage log):**
   - เครื่องมือที่ใช้และวัตถุประสงค์
   - **ตัวอย่างคอนกรีตอย่างน้อย 2 กรณีที่ AI ให้คำแนะนำผิดพลาด** วิธีการตรวจพบ และวิธีที่คุณแก้ไข
3. **คำถามเชิงการออกแบบ (ตอบสั้นๆ ย่อหน้าละหัวข้อ):**
   - **Q1:** ความแตกต่างระหว่าง Lifecycle ของ `GetxController` กับ `State` ของ Widget ใน codebase นี้คืออะไร? และระบุบั๊กจาก Part A ที่เกิดจากความสับสนนี้
   - **Q2:** การครอบ Subtree ขนาดใหญ่ด้วย `Obx` ตัวเดียวส่งผลเสียอย่างไร? และมีเกณฑ์อย่างไรในการกำหนดขอบเขต Reactivity?
   - **Q3:** จะเขียน Automated test อย่างไรเพื่อตรวจจับบั๊ก RES-106 ก่อนการ Release? และต้องปรับเปลี่ยนโค้ดส่วนใดบ้างเพื่อให้สามารถทดสอบได้?
4. **ระยะเวลาที่ใช้จริงโดยประมาณ** และสิ่งที่จะทำต่อหากมีเวลาเพิ่มอีก 1 วัน

## เกณฑ์การประเมิน (How we grade)

- **คุณภาพการวิเคราะห์สำคัญกว่าปริมาณ:** การหาสาเหตุและแก้ไขอย่างถูกต้อง 5 ตั๋ว ได้คะแนนดีกว่าการแก้แบบฉาบฉวยครบทั้ง 7 ตั๋ว

- **กระบวนการคิดและการตัดสินใจ:** การออกแบบพฤติกรรมในส่วนที่โจทย์ไม่ได้ระบุรายละเอียด
- **กระบวนการทำงาน:** ประวัติการคอมมิท (Commit history), ความตรงไปตรงมาเกี่ยวกับงานที่ยังไม่เสร็จ และ AI usage log
